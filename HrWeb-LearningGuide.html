Kiến trúc 3 tầng (3-Layer Architecture)

Đây là pattern nền tảng của mọi backend Java. Toàn bộ project HrWeb đều tuân theo cấu trúc này:

Controller
Nhận HTTP request, gọi Service, trả HTTP response. Không chứa logic nghiệp vụ.
Service
Xử lý toàn bộ business logic, validation, tính toán. Đây là trái tim của ứng dụng.
Repository
Chỉ giao tiếp với database. Không chứa logic, chỉ chứa query.

Ví dụ từ project: Luồng tạo đơn nghỉ phép

POST /api/v1/leave-requests
→
LeaveRequestController
→
LeaveRequestService
→
LeaveRequestRepository
→
MySQL

Code minh họa

// Controller — chỉ nhận request và gọi service
@PostMapping
public ResponseEntity<LeaveResponse> create(
    @RequestBody LeaveRequest request,
    @AuthenticationPrincipal UserDetails user) {
    return ResponseEntity.ok(
        leaveRequestService.createLeaveRequest(user.getUsername(), request)
    );
}

// Service — xử lý business logic
public LeaveResponse createLeaveRequest(String email, LeaveRequest req) {
    // Validate: ngày hợp lệ? Còn phép không? Trùng đơn không?
    if (!req.getStartDate().isAfter(LocalDate.now()))
        throw new RuntimeException("Phải xin nghỉ trước ít nhất 1 ngày!");
    // ... lưu database
}
💡 Bài học Quy tắc vàng: nếu bạn viết SQL query hoặc business logic trong Controller, đó là sai. Mỗi tầng chỉ làm đúng 1 việc.

DTO Pattern — Tách biệt dữ liệu API và Database

DTO (Data Transfer Object) là lớp trung gian giữa API và database. Project dùng 2 loại DTO:

LoạiVị tríMục đích
Request DTOdto/request/Nhận dữ liệu từ client gửi lên
Response DTOdto/response/Trả dữ liệu về cho client

Tại sao không trả Entity thẳng ra API?

// ❌ SAI — trả Entity thẳng ra
@GetMapping("/{id}")
public Employee getEmployee(@PathVariable Long id) {
    return employeeRepository.findById(id).get();
    // Vấn đề: lộ password, salary, các quan hệ phức tạp
    // JSON bị vòng lặp vô hạn: Employee → Department → Manager → Employee...
}

// ✅ ĐÚNG — dùng Response DTO
@GetMapping("/{id}")
public EmployeeResponse getEmployee(@PathVariable Long id) {
    Employee emp = employeeRepository.findById(id).get();
    return EmployeeResponse.builder()
        .id(emp.getId())
        .fullName(emp.getFirstName() + " " + emp.getLastName())
        .department(emp.getDepartment().getName())
        // password và salary bị ẩn đi
        .build();
}
⚠️ Lưu ý Với Lombok, dùng @Builder trên DTO để tạo object gọn gàng. Project này đã làm đúng điều này.

JWT Authentication — Xác thực không dùng session

JWT (JSON Web Token) là cách xác thực phổ biến nhất cho REST API hiện đại. Project dùng JWT thay vì session truyền thống.

So sánh Session vs JWT

Session truyền thốngJWT (dùng trong project)
Lưu stateServer lưu sessionServer không lưu gì
ScaleKhó (phải sync session)Dễ (mỗi server tự verify)
Cách hoạt độngSessionID trong cookieToken trong header

Luồng JWT trong project này

1. Client
→ POST /api/v1/auth/login với email + password
2. Server
→ Verify password → tạo JWT token (24h) → trả về client
3. Client
→ Lưu token vào localStorage, gửi kèm mọi request tiếp theo
4. JwtFilter
→ Chặn mọi request, verify token → cho phép hoặc từ chối

Cấu trúc JWT Token

eyJhbGciOiJIUzI1NiJ9         ← Header (thuật toán HMAC-SHA256)
.eyJzdWIiOiJ1c2VyQGhyLmNvbSIsInJvbGUiOiJBRE1JTiJ9  ← Payload (email, role)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c       ← Signature (chữ ký)

Code verify JWT

// JwtAuthenticationFilter.java — chạy trước mọi request
@Override
protected void doFilterInternal(HttpServletRequest request, ...) {
    String token = extractToken(request);   // Lấy token từ header
    if (token != null && jwtUtil.validateToken(token)) {
        String email = jwtUtil.getEmailFromToken(token);
        // Đặt authentication vào SecurityContext
        UsernamePasswordAuthenticationToken auth = new UsernamePasswordAuthenticationToken(
            email, null, getAuthorities(token));
        SecurityContextHolder.getContext().setAuthentication(auth);
    }
    filterChain.doFilter(request, response);
}
🔴 Lỗi trong project này JWT secret đang là "yourVeryStrongSecretKey123456789" — quá yếu và dễ đoán. Trong thực tế phải dùng key ngẫu nhiên 256-bit và lưu trong environment variable.

OAuth2 với Google — Đăng nhập bằng Google

Project cho phép đăng nhập bằng Google account thay vì tự nhập email/password. Đây là tính năng rất phổ biến.

Luồng OAuth2

1. Click "Login Google"
→ Redirect tới trang đăng nhập của Google
2. Google xác thực
→ Trả về authorization code cho backend
3. Backend
→ Đổi code lấy user info (email, tên) từ Google
4. OAuth2SuccessHandler
→ Tạo Employee mới (nếu chưa có) + tạo JWT → redirect về frontend

Class quan trọng

FileNhiệm vụ
OAuth2AuthenticationSuccessHandler.javaXử lý sau khi Google xác thực thành công
CustomOAuth2UserService.javaLấy thông tin user từ Google, tạo Employee nếu mới
SecurityConfig.javaCấu hình endpoint OAuth2, redirect URI
💡 Bài học Spring Boot xử lý hầu hết luồng OAuth2 tự động. Bạn chỉ cần cấu hình client-id, client-secret và viết SuccessHandler để tạo JWT sau khi đăng nhập thành công.

// Cách 2: Kiểm tra trong SecurityConfig — bảo vệ toàn bộ URL pattern

JPA & Hibernate — Thao tác Database

Project dùng Spring Data JPA để tương tác với MySQL mà không cần viết SQL thủ công.

3 cách viết query trong project

// Cách 1: Method name — Spring tự sinh SQL
List<Employee> findByDepartment(Department dept);
// → SELECT * FROM employees WHERE department_id = ?

Optional<Employee> findByEmail(String email);
// → SELECT * FROM employees WHERE email = ?

// Cách 2: @Query — viết JPQL tùy chỉnh
@Query("SELECT e FROM Employee e WHERE " +
       "(:name IS NULL OR LOWER(e.firstName) LIKE %:name%) AND " +
       "(:deptId IS NULL OR e.department.id = :deptId)")
Page<Employee> searchEmployees(@Param("name") String name,
                                @Param("deptId") Long deptId, Pageable pageable);

// Cách 3: Pagination tự động
Page<Employee> findAll(Pageable pageable);
// Pageable pageable = PageRequest.of(page, size, Sort.by("name"));

Quan hệ giữa các Entity

// Employee thuộc 1 Department (Many-to-One)
@ManyToOne
@JoinColumn(name = "department_id")
private Department department;

// Department có nhiều Employee (One-to-Many)
@OneToMany(mappedBy = "department")
private List<Employee> employees;

// Chú ý: quan hệ 2 chiều → dễ bị vòng lặp khi serialize JSON
// → Dùng DTO để tránh vấn đề này (xem Section 2)
⚠️ Lưu ý quan trọng spring.jpa.hibernate.ddl-auto=update trong project nghĩa là Hibernate tự tạo/cập nhật bảng khi start. Trong production nên dùng validate và quản lý schema bằng Flyway/Liquibase.

Những lỗi phổ biến trong dự án — Rút kinh nghiệm

🔴 Lỗi 1 — API Key & Secret hardcode trong source code

File application.properties chứa Gemini API key và JWT secret dạng plaintext. Nếu push lên GitHub, key bị lộ ngay lập tức.

Chuẩn: Dùng environment variable ${GEMINI_API_KEY} hoặc file .env trong .gitignore.

🔴 Lỗi 2 — userContext không được gửi lên Gemini (đã sửa)

Code gốc xây dựng biến userContext (tên, phòng ban, role người dùng) nhưng không bao giờ đưa vào request gửi Gemini. AI không biết đang nói chuyện với ai.

Sửa: Đưa userContext vào systemInstruction trong mỗi lần gọi Gemini API.

⚠️ Lỗi 3 — N+1 Query Problem

Method getDepartments() query database 1 lần cho mỗi phòng ban để đếm nhân viên. Nếu có 20 phòng ban = 21 queries.

Chuẩn: Dùng GROUP BY department_id để lấy toàn bộ trong 1 query duy nhất.

⚠️ Lỗi 4 — AI layer không tái sử dụng Service layer

Hàm createLeaveRequest() trong AiService tự xử lý logic thay vì gọi LeaveRequestService có sẵn. Kết quả: thiếu validation overlap đơn nghỉ phép.

Chuẩn: AI function chỉ nên gọi Service layer, không tự xử lý business logic.

⚠️ Lỗi 5 — Thiếu Unit Test hoàn toàn

Project không có bất kỳ test nào. Sửa 1 chỗ có thể vô tình phá chỗ khác mà không biết.

Chuẩn: Viết JUnit + Mockito test cho Service layer, đặc biệt là business logic phức tạp.
